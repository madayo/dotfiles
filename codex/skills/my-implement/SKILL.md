# my-implement

承認済みの変更を実装し、受け入れ条件に対応する検証結果を返す。共通の作業ルールは `AGENTS.md` が参照する `AI_RULES.md` に従い、ここでは設計から実装への受け渡しを扱う。

## 実装の前提を確認する

- 会話または提示された資料から、要件・受け入れ条件、採用する方針、承認の対象を確認する。
- 実装スキルの選択・呼び出しだけでは、未提示の設計が承認されたと扱わない。方針がない場合は関連コードを確認し、具体的な変更・影響・検証方法を提案して承認を待つ。承認の再確認は共通ルールに従う。
- 設計時からの要件・関連コードの変更、現在のブランチと作業ツリーを確認する。ユーザーや他の作業の変更を上書きせず、今回の変更範囲を識別する。

## 実装・検証する

- 承認された範囲で変更する。設計内の通常の実装詳細は既存パターンに沿って判断し、逐一の承認を要求しない。
- 調査で前提が崩れ、挙動・互換性・変更範囲・データ操作などの重要な方針変更が必要になった場合は、理由と改訂案を提示して承認を待つ。
- 受け入れ条件と想定する失敗条件に対して、適切な既存テスト、静的検査、実行・ログ確認を行う。追加テストは、意味のある回帰防止が必要な場合に用意する。
- 失敗した確認は原因を確認し、今回の変更に起因する問題を承認範囲内で修正する。既存の失敗や環境制約を隠すために関係のないコード・設定を変更しない。
- 検証が実行できなければ、理由、未確認の挙動、代替確認の結果を示す。未実行の確認を成功扱いにしない。
- 最終差分を要件適合、副作用、セキュリティ、エッジケース、可読性の観点でセルフレビューする。

## 結果を返す

変更した動作と理由、主な変更ファイル、実行した検証と結果、残る制約を簡潔に報告する。
コードからの判断と実行で確認した内容を区別し、受け入れ条件に未確認部分があれば明示する。

独立レビューが必要なら対象範囲を添えて提案する。実施手順は `my-review` に従う。
commit・push・PR 作成も実装の呼び出しだけで許可されたと扱わない。別途指示がある場合はその範囲で進める。
