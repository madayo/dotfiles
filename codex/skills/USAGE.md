# 開発スキルの使い方

個人用の `my-*` スキルについて、人間向けの依頼例をまとめています。
**調査・設計・実装・レビューは、日本語で目的と条件を伝えるだけで十分です。**
Codex が必要な工程を選び、依頼範囲内で進めます。途中で別のスキルを指定し直す必要もありません。
PR 作成・Copilot 対応・引き継ぎは、後述のスキル名を明示して呼び出します。

以下の使用順は例です。実際の構成はコードや調査結果により変わります。
選択のルールは [AGENTS.md](../../.codex/AGENTS.md)、共通の承認・作業ルールは [AI_RULES.md](../../AI_RULES.md)、各工程の詳細は各スキルの `SKILL.md` にあります。

## モデルと推論レベル

ユーザーと対話するメインは、作業開始時に、依頼内容に応じた判定行と推奨するモデル・推論レベルを案内し、「現在の設定のまま進める」か「モデル・推論レベルを変更してから進める」かの判断を待ちます。変更する場合はユーザーが `/model` で切り替え、変更完了と続行を伝えてください。Codex はメインの現在設定や利用可能なモデルを調べません。

指示ファイルの読み込みと初動判定を除き、回答前に作業を始めません。同じ作業で推奨値が変わらなければ確認を繰り返さず、推奨値が変わる場合は再提示して判断を待ちます。

親がモデル・推論レベルを明示指定して起動するサブエージェント・組み込みレビューは、この回答待ちの対象外です。親の会話履歴がなくても指定範囲を実行し、設定の不足・利用不能は親へ報告します。変更・外部操作などに必要な承認は省略しません。

推奨・明示指定するモデルは `gpt-6.1-sol` と `gpt-6-luna` に限定します。通常と、判断に迷って上位の条件を採用する場合は **`gpt-6.1-sol` / `high` まで**です。`xhigh` は、その作業について `high` では不足し、`xhigh` が最適だとする具体的な理由と期待する改善を示せる場合だけ選び、最重設定を **`gpt-6.1-sol` / `xhigh`** とします。`max`・`ultra` は使いません。Astra・過去モデルは、ユーザーがその使用を明確に指示した場合だけ、指定された範囲で使用します。モデルの指定だけで推論レベルの上限は変更しません。この制限はメインへの推奨とサブエージェント・組み込みレビュー・独立レビューへの設定指定に適用し、個別スキルや親の設定だけを理由に `xhigh` を選びません。許可した設定が利用できない場合も、ユーザーの明確な指示なく Astra・過去モデルでは代用しません。

判定表と委譲条件は [AGENTS.md の「モデルと推論レベルの提案」](../../.codex/AGENTS.md#モデルと推論レベルの提案) を参照してください。作業中に判定行が変われば工程の切れ目で再提案します。委譲では作業ごとにモデル・推論レベルを指定し、設計判断はメインで行います。レビューには `my-review` の設定を使います。

作業の完了時に `~/.codex/model-routing-log.md` へ1作業1行で記録します。書き込み禁止のモードでは省略し、最終報告に「ログ未記録（書き込み不可）」と明記します。効果を確認したいときは「モデル選定ログを読んで、提案・委譲が適切だったか評価して」と依頼できます。

## 自動選択するスキル

| スキル | 担当する工程 |
| --- | --- |
| [my-investigate](my-investigate/SKILL.md) | 原因・既存動作・変更影響の調査 |
| [my-design](my-design/SKILL.md) | 変更方針・影響・検証方法の設計 |
| [my-implement](my-implement/SKILL.md) | 承認済み方針の実装・検証・最終差分の基本確認 |
| [my-implement-wt](my-implement-wt/SKILL.md) | worktree 上での実装・静的確認・ローカル commit（実行検証は保留） |
| [my-verify](my-verify/SKILL.md) | worktree モードで保留した検証をメインツリーで再開 |
| [my-review](my-review/SKILL.md) | レビュー構成の提示と実行 |

Codex の実装・検証工程では必要なテスト・動作確認と、意図しない変更・デバッグコード・秘密情報の混入がないかの基本確認を行います。詳細なレビューは最後にユーザーが指示する `my-review` へ分担し、実装工程では重複して行いません。未実施なら「詳細レビュー未実施」と報告します。この分担は Codex 固有の方針とし、他エージェントのレビュー手順は変更しません。

## 現状の仕様を調べたい

```text
退会済みユーザーが管理画面の検索対象に含まれる条件を調べて。
コード上の条件と既存テストの有無を示して。変更は不要。
```

想定する工程は `my-investigate` のみです。調査結果を返して終了します。

## 原因不明の不具合を直したい

```text
注文一覧で同じ注文が二重に表示される不具合を直したい。
発生するのは絞り込み後の2ページ目。期待動作は注文IDごとに1件の表示。
表示順と既存の絞り込み条件は維持して。
```

想定する工程は調査 → 必要なら設計 → 方針の承認 → 実装・検証です。
原因と修正方法が明確になれば、別の設計工程を設けず、実装工程内で方針を提案する場合もあります。
提示された方針を確認した後は、次のように返せます。

```text
提示した方針で承認します。実装と検証を進めて。
```

## 原因と方針が明確な修正をしたい

```text
空文字の検索条件がAPIへ送られてエラーになるので、
既存の検索条件の組み立て箇所で空文字だけを除外してほしい。
0とfalseは送信対象として維持して。
```

想定する工程は `my-implement` です。未承認の方針を具体化してから確認します。
同じ方針が既に承認済みなら、その確認を繰り返しません。

## 機能を追加したい・設計だけ相談したい

```text
管理画面の注文一覧にCSV出力を追加してほしい。
対象は現在の絞り込み条件に一致する全件で、画面の1ページ分ではない。
出力項目は注文ID・注文日時・金額。既存の閲覧権限を適用して。
```

想定する工程は `my-design` → 方針の承認 → `my-implement` です。
既存構造の不確実さが大きければ、その前に調査を含めます。
設計だけ相談したい場合は「まず方針の比較まで。実装は不要」と添えると、その範囲で終了します。

## worktree で実装し、検証を後から再開したい

```text
注文一覧のCSV出力を worktree で実装して。
docker での検証はメインツリーが空いてから行いたい。
```

「worktree」を実行方法として指定すると worktree モードになります。想定する工程は設計（メインツリー）→ 方針の承認 → `my-implement-wt` → `my-verify` → 必要ならレビューです。
質問への回答とスキルの直接指定が優先され、「worktree について調べて」のような話題としての言及では切り替わりません。

方針にはブランチ・worktree のパス・起点・保留する検証と、ローカル commit（push はしない）を含めます。承認後、`.codex/worktrees/<name>` で実装と静的確認を行い、commit と `<git-common-dir>/codex-verify/<ブランチ名>.md` の検証待ちメモを残します。通常の実装方針を承認した後で worktree モードへ変更する場合は、commit を含む実行モードだけを追加で確認します。

メインツリーで作業していた別セッションの操作を終えてから、同じセッションで次のように伝えます。

```text
メインが空いたから戻って検証を再開して。
```

`my-verify` がメインツリーへ操作先を移し、対象 worktree を取り外してブランチを切り替え、保留した検証を行います。未コミット変更や、削除される ignore 済みファイルがあれば停止・確認します。依存は切り替え前の lockfile と docker のインストール状態も確認し、必要なら再インストールします。
検証中の修正は未 commit のまま残し、未確認があればメモを更新します。すべて確認できたらメモを削除し、対象ブランチに留まります。

## 変更をレビューしてほしい

```text
今回の未コミット・未追跡の変更をレビューしてほしい。
Codex関連の範囲だけを対象にして、要件と設計の整合性も確認したい。
```

`my-review` が対象・構成・モデル・effort を示します。メインの推奨設定を初めて提示する場合や推奨値が変わる場合は、現在のまま進めるか変更するかの判断を待ちます。同一作業で同じ推奨値への判断が済んでいれば再確認せず、読み取り専用のレビューと必要な検証を進めます。対象が曖昧な場合は確認します。修正・commit・push・PR 作成は別途指示が必要です。

指摘への対応は「#1 と #3 の修正方針を提案して。#2 は修正しない」のように番号で依頼できます。

## 明示呼び出し専用のスキル

以下の3つは、自動選択や他工程からの自動追加を行いません。

### PR 作成（[my-pr](my-pr/SKILL.md)）

```text
$my-pr 今回のCSV出力機能の変更でPRを作成して。
レビュー結果と実行した検証をPR本文に反映して。
```

提示されたブランチ・コミット内容、push、PR タイトルを確認し、必要な承認に回答します。PR 本文は確認対象に含めず、チャットにも出力しません。タイトルの承認後に、既存形式の日本語本文を作成して PR を作成します。

### Copilot 対応（[my-copilot-review](my-copilot-review/SKILL.md)）

```text
$my-copilot-review 現在のPRのCopilot指摘を確認して、採用・不採用の理由を教えて。
修正とコメント投稿は、内容を確認するまで待って。
```

`my-copilot-review` が指摘を取得し、番号付きで採否を説明します。
修正案を確認した後は「#1 と #3 の修正案を承認します。修正と検証を進めて」と返せます。
対応結果と返信案を確認した後に「提示したコメントをPRに投稿して」と依頼します。
修正コードの commit・push は別途指示が必要です。コメント投稿だけではコードはリモートへ反映されません。

### 引き継ぎ（[my-handoff](my-handoff/SKILL.md)）

```text
$my-handoff 会話が長くなったので、新しいチャットへ移るための引き継ぎメモを作って。
承認済み設計、変更済みファイル、検証結果、未対応の指摘を残して。
次の依頼は「未対応の #3 の修正方針を提案する」にしたい。
```

`my-handoff` が作業ディレクトリ直下に `tmp-handoff.md` を出力します。
同名ファイルがあれば、処理を続ける前に確認が入ります。
新しいチャットではメモの「引き継ぎ本文」を貼るか、同じ作業ディレクトリで次のように依頼します。

```text
tmp-handoff.md を読み、記載された次の依頼を進めて。
```

## スキルや範囲を明示したい場合

自動選択に任せず、工程や対象を指定することもできます。

```text
$my-design CSV出力の設計だけを提案して。実装は不要。
```

```text
$my-review master...HEAD のコミット済み差分だけを対象にして。
未コミット変更は対象外にして。
```

`my-review` は比較範囲の指定がなければ、ローカルの main / master とのコミット済み差分を基準にします。
未コミット・未追跡の変更を見たい場合は、上のレビュー例のように明示してください。

## 配置

`bin/initialize/_link.sh` は各スキルを `~/.codex/skills/` へ個別にリンクします。
新しいスキルが現在のセッションの一覧に現れない場合は、新しいチャットで利用してください。
