# my-review

変更の規模・リスクとレビュー履歴から最適な構成を提案し、承認後に実施する。
一度の指示で対象確認・構成提案まで進め、レビューの実行前にユーザーの最終判断を待つ。

## 役割分担

- メインエージェント: 対象・要件・履歴・リスクの確認、構成提案、承認待ち、実行、結果の集約。
- 組み込み `codex review`: 不具合、回帰、副作用、エッジケース、セキュリティ上の問題、テスト不足の検出。
- 独立したサブエージェント: 要件適合、設計の妥当性、既存設計との整合性、不要な複雑さ、命名・保守性の評価。
- テスト・動作確認: レビューとは別の検証。既存の実行結果を確認し、不足する検証の実行は構成提案に含める。

組み込みレビューの詳細チェックをこのスキル内で再実施しない。必要な場合は実際にコマンドを呼び出す。

## 1. 対象と要件を確認する

この段階では構成選定に必要な読み取りだけを行い、本レビュー・サブエージェント起動・テスト実行は承認後に行う。

- 引数なし: ローカルの `master` または `main` を比較元とし、`git diff <base>...HEAD`（共通祖先から HEAD までのコミット済み変更）を対象とする。片方だけ存在する場合はそれを使う。両方存在する場合は、この依頼で既に指定・承認された比較元があればそれを使い、なければどちらを使うか質問する。どちらも存在しない、または共通祖先を確認できない場合も比較元を質問する。リモートブランチや PR のベースへ自動で切り替えない。
- `git status --short --branch`、`git diff --cached`、`git diff`、`git ls-files --others --exclude-standard` で作業ツリーの状態も確認する。未コミット・未追跡の変更は `<base>...HEAD` に含まれないため、存在する場合は追加対象にするか構成提案時に確認する。無断で追加しない。追加する場合は別の対象として明示し、新規ソースも確認する。秘密情報や生成物を無条件に収集しない。
- 引数あり: 全体を自然言語の追加指示として受け取り、比較範囲・重点観点・実行方法・モデル・effort の意図を読み取る。引数全文を `git diff` やシェルに直接渡さない。抽出した参照やパスは確認したうえで、安全な Git 引数として渡す。
  - 比較範囲の指定がなければ、引数なしと同じ基準で `master` または `main` を選び、`<base>...HEAD` を提案する。指定がある場合はその意図を優先し、不明点だけ質問する。
  - 例: 「認可を重点的に確認して」は既定の範囲への重点指示。「HEAD~1 の変更を見て」は単一コミットか `HEAD~1` から作業ツリーまでか曖昧なら確認する。「A..B の設計を確認して」はその比較範囲と設計観点への指示として扱う。
  - 解釈した対象・重点観点・実行方法を構成提案に示す。追加指示があっても、レビュー実行前の承認は省略しない。
- 差分が空でも、現ブランチ、未追跡ファイル、比較元、直近コミットを確認してから「変更なし」と報告する。
- 元の依頼・受け入れ条件・承認済みの制約を特定する。承認済みの設計は要件と区別する。要件・対象の不明点が構成や評価に影響する場合は質問し、推測で補わない。

## 2. 既存レビューを確認する

同一セッション内のツール実行結果・レビュー結果、およびユーザーが提示した記録を確認する。
「セルフレビューした」「問題なし」という発言だけでは組み込みレビューの実施済み扱いにしない。

再利用には以下の確認が必要。

- 種類・実行方法・完了結果: 組み込みレビュー、要件・設計レビュー、テストを区別する。失敗・中断は完了扱いにしない。
- 対象: リポジトリ、比較方法、比較元の SHA、対象の HEAD / コミット SHA、対象ファイル。
- 作業ツリーの識別情報: staged / unstaged 差分と未追跡の対象ファイルのパス・内容を含むハッシュ。ファイル内容や秘密情報自体は記録に残さない。
- 実行時のモデル・effort と、その確認根拠。記録がなければ「設定不明」とする。
- レビュー後のコード変更、要件・制約の変更、および未解決の指摘。

同じ対象・範囲に対する完了済みレビューで、その後に対象内容や評価に関わる要件の変更がなければ再利用する。
局所レビューをブランチ全体のレビューとして扱わない。指摘が残っている場合は結果を引き継ぎ、解決済みとはみなさない。
変更があれば変更箇所と影響範囲の再レビューを提案する。組み込みコマンドでその範囲を正確に指定できない場合は、適切な全体範囲の再レビューを提案する。
識別情報が不足して同一性を確認できない場合は「履歴確認不能」と明示し、再実行の要否を承認時に確認する。
モデル・effort が低い、異なる、または不明という理由だけで有効な既存レビューを無効にしない。追加レビューを提案する場合は、今回のリスクに対して不足する確認と再実行の理由を説明する。

## 3. 構成を提案し、承認を待つ

ファイル数・行数だけで判定せず、動作変更の有無、影響範囲、仕様・設計の変更、データや権限への影響で判断する。

| 変更の性質 | 推奨する構成 |
| --- | --- |
| 文言・コメントなど動作に影響しない変更 | 簡易差分確認 |
| 局所的なバグ修正 | 組み込みレビュー |
| 機能追加・仕様変更・リファクタリング | 組み込み → 独立した要件・設計レビュー |
| 認証・認可・決済・データ更新・DB変更など影響の大きい変更 | 組み込み → 独立した要件・設計レビュー ＋ 重点的な検証結果の確認 |

小規模でも設計判断を含む場合は要件・設計レビューを追加する。実施済みの有効なレビューは省略し、残る確認だけを提案する。
新たに実施すべきレビュー・検証がない場合は、判定理由と既存結果・未解決事項を報告して終了する。結果の再掲だけのために承認を求めない。
簡易差分確認は意図した文言・変更範囲の確認に限定する。動作への影響が判明した場合は構成を見直す。

### モデル・effort の選定

- メインでの構成判断・結果集約は現在のセッション設定で行う。レビューのためにメインセッションや共通設定ファイルを変更しない。
- 現在の実効モデル・effort を、利用できるセッション情報から確認する。設定ファイルの値は初期設定であり、セッション中の変更や起動時の上書きがあり得るため、実効値と同一だと推測しない。確認できない場合は「現在の設定不明」と示し、使用する具体的な設定をユーザーと確認する。
- レビュー用モデルは原則メインと同じ。利用可能性・対応 effort を確認し、モデル名と effort をセットで提案する。別モデルを選ぶ場合は選定理由を示し、承認を得る。
- 目安: 単純な局所修正は `medium`、機能追加・設計変更・複数箇所に影響する修正は `high`。認可・決済・移行・並行処理などは利用可能な高能力モデルの `high` を基本に、特に難しい場合は `xhigh` を提案する。これは運用上の目安であり、モデルが対応する値とユーザーの指定を優先する。
- 既に高い effort が選ばれている場合は勝手に下げない。異なるモデル間では effort 名だけで能力の優劣を判断しない。簡易差分確認はメインの現在の設定で行う。
- 第三者視点は履歴を引き継がないことを優先し、別モデルへの変更を必須にしない。重要な設計判断や評価が割れる問題では、追加時間・使用量も含めて別モデルの追加レビューを提案できる。
- `/review` の `review_model`、別プロセスの `codex review` の設定、サブエージェントの継承・既定値は区別する。メインの設定がすべてに自動適用されると扱わない。

提案には次を含め、最後に「この構成で実施してよいですか？」と確認して停止する。

- 対象範囲、追加指示の解釈・重点観点、規模・リスクの判定とその理由。未コミット・未追跡変更がある場合は追加対象にするかも確認する。
- 再利用するレビューと、その対象・完了根拠。省略できない場合の理由。
- 実施するレビュー、順序、担当、必要なテスト・動作確認。
- 各レビューのモデル・effort・選定理由、メインの設定から変更する点。再利用するレビューの設定が不明ならその旨も示す。
- 不明点・未確認事項。サブエージェントや組み込みコマンドが利用できない場合の代替案。

このスキルの呼び出し自体を実行承認と解釈しない。ただし、同じ対象・構成・モデル・effort に対する明示的な承認が既にある場合は再承認を求めない。
承認後に対象やリスクが変わり、構成・範囲の拡大が必要になった場合は、その理由と追加作業を示して再承認を待つ。
承認されたモデル・effort を利用できない場合や変更が必要な場合は、黙って別設定へ切り替えず、理由と代替設定を提示して再承認を待つ。

## 4. 承認されたレビューを実施する

開始前に対象の識別情報を再確認する。順序は原則として組み込みレビュー → 要件・設計レビュー → 結果の集約とする。

### 組み込みレビュー

- 作業ツリー: `codex review --uncommitted`（staged / unstaged / 未追跡）。
- ベースブランチ比較: `codex review --base <branch>`。
- 単一コミット: `codex review --commit <sha>`。
- 任意の比較範囲: `codex review` のカスタム指示で比較方法と範囲を明示する。`A..B` と `A...B` を勝手に置き換えない。

`--uncommitted`、`--base`、`--commit`、カスタム指示は併用せず、いずれか一つを使う。実行前に利用中の `codex review --help` と照合する。
追加指示を組み込みレビューへ渡す場合は、承認された比較方法・対象範囲と重点指示をまとめたカスタム指示を使用する。要件・設計など担当外の指示は独立レビューへ渡す。組み込みの実際の対象範囲が承認された範囲と一致することを確認し、`<base>...HEAD` に未コミット変更が混ざるなど一致しない場合もカスタム指示で範囲を明示する。
承認された設定をその実行だけに明示指定する。対応する CLI では `-c 'model="<model>"' -c 'review_model="<model>"' -c 'model_reasoning_effort="<effort>"'` を付け、既存の `review_model` による意図しないモデル選択も避ける。モデル・effort の指定を自然言語の指示だけで代用しない。
カスタム指示は構造化引数または stdin で安全に渡す。このスキルを再起動せず、組み込みのレビューだけを実施するよう指定する。
コマンドの完了と出力を確認する。利用不能・失敗時は未実施と報告し、メインエージェントのレビューで黙って代用しない。代替構成は承認を得る。

### 独立した要件・設計レビュー

この工程ではサブエージェントへ委譲する。親の会話履歴を継承しない新規コンテキストで起動する（`fork_turns="none"` が使える環境ではそれを指定）。
承認されたモデル・effort を起動パラメータで明示指定する（対応する環境では `model` / `reasoning_effort`）。カスタムエージェント設定による上書きも確認し、親からの継承や既定値に任せない。指定できない環境では、解決される設定を確認して承認された値と一致する場合のみ実行し、確認できなければ代替案の承認を待つ。

- 渡す情報: ユーザーの要件・受け入れ条件、担当範囲に関わるユーザーの追加指示と承認された解釈、承認済みの制約、要件と区別した設計、リポジトリと対象範囲・識別情報、適用される `AGENTS.md`、関連資料の場所。重点指示は確認の優先度として扱い、問題の存在や結論を前提にしない。
- 渡さない情報: 実装担当の評価・自己正当化、既存レビューの結論、メインエージェントが付け加えた誘導的な懸念や期待する回答。元の要件・追加指示をメインエージェントの解釈だけに置き換えない。
- 担当範囲: 要件の不足・逸脱、要件外の変更、設計の妥当性と既存設計との整合性、不要な抽象化・冗長さ、命名・保守性。
- コードと関連実装を自ら調査し、根拠付きの指摘・修正案・要確認事項を返すよう依頼する。独自の不具合・セキュリティチェックや `my-review` の再起動は依頼しない。
- 読み取り専用の作業とし、修正・追加エージェントの起動は行わせない。スコープ外でも重大な問題に気づいた場合は根拠とともに報告する。

結果を待ってから集約する。新規コンテキストでの委譲ができなければ、その制約を説明して代替案の承認を待つ。
メインエージェントは指摘の根拠を確認し、採否を説明する。実装時の方針と違うことだけを理由に却下しない。

## 5. 結果を報告する

- findings を先に、重要度順に提示する。指摘には `#1` からの一意の番号を付け、後続の相談・再レビューでも維持する。追加指摘は未使用の番号を使う。
- 組み込みと要件・設計レビューの重複指摘は集約し、出典・重要度・ファイルと行・問題・影響・修正案を示す。
- 指摘がない場合は「指摘なし」とし、確認できた範囲と残る不明点・検証不足を記載する。指摘がないことを全観点の安全保証や未実行テストの成功に置き換えない。
- 「コード上で確認」「テスト・実行結果で確認」「未確認」を区別する。
- 実施／再利用／未実施のレビューと理由、検証結果、次のアクションを記載する。
- 次回の重複防止のため、各レビューの種類・実行方法・モデル・effort・完了状態・対象識別情報・要件の参照元・結果を会話内に記録する。モデル・effort は指定値と、実行情報で確認できた実効値を区別し、確認不能な値を確認済みとしない。終了時にも対象を確認し、実行中の変更があれば結果が適用できる範囲を明示する。

レビューの承認にはコード修正・commit・push・PR 作成を含めない。修正はユーザーの許可を得てから行う。
