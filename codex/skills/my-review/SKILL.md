# my-review

`AGENTS.md` に従い、作業開始時やメインの推奨設定が変わる場合は、推奨を示してユーザーの判断を待つ。同一作業で同じ推奨値への判断が済んでいれば再確認しない。
判断後、変更の規模・リスクとレビュー履歴から構成を選び、ユーザーに示して実施する。
対象や要件に実行を左右する不明点がある場合だけ質問する。

## 役割分担

- メインエージェント: 対象・要件・履歴・リスクの確認、構成提示、実行、結果の集約。
- 組み込み `codex review`: 不具合、回帰、副作用、エッジケース、セキュリティ上の問題、テスト不足の検出。
- 独立したサブエージェント: 要件適合、設計の妥当性、既存設計との整合性、不要な複雑さ、命名・保守性の評価。
- テスト・動作確認: レビューとは別の検証。既存の実行結果を確認し、不足する検証の実行は構成に含める。

組み込みレビューの詳細チェックをこのスキル内で再実施しない。必要な場合は実際にコマンドを呼び出す。

## 1. 対象と要件を確認する

この段階では構成選定に必要な読み取りだけを行い、本レビュー・サブエージェント起動・テスト実行は構成を示した後に行う。

- 引数なし: ローカルの `master` または `main` を比較元とし、`git diff <base>...HEAD`（共通祖先から HEAD までのコミット済み変更）を対象とする。片方だけ存在する場合はそれを使う。両方存在する場合は、この依頼で既に指定・承認された比較元があればそれを使い、なければどちらを使うか質問する。どちらも存在しない、または共通祖先を確認できない場合も比較元を質問する。リモートブランチや PR のベースへ自動で切り替えない。
- `git status --short --branch`、`git diff --cached`、`git diff`、`git ls-files --others --exclude-standard` で作業ツリーの状態も確認する。未コミット・未追跡の変更は `<base>...HEAD` に含まれないため、存在する場合は追加対象にするか構成提案時に確認する。無断で追加しない。追加する場合は別の対象として明示し、新規ソースも確認する。秘密情報や生成物を無条件に収集しない。
- 引数あり: 全体を自然言語の追加指示として受け取り、比較範囲・重点観点・実行方法・モデル・effort の意図を読み取る。引数全文を `git diff` やシェルに直接渡さない。抽出した参照やパスは確認したうえで、安全な Git 引数として渡す。
  - 比較範囲の指定がなければ、引数なしと同じ基準で `master` または `main` を選び、`<base>...HEAD` を対象にする。指定がある場合はその意図を優先し、不明点だけ質問する。
  - 例: 「認可を重点的に確認して」は既定の範囲への重点指示。「HEAD~1 の変更を見て」は単一コミットか `HEAD~1` から作業ツリーまでか曖昧なら確認する。「A..B の設計を確認して」はその比較範囲と設計観点への指示として扱う。
  - 解釈した対象・重点観点・実行方法を構成に示す。
- 差分が空でも、現ブランチ、未追跡ファイル、比較元、直近コミットを確認してから「変更なし」と報告する。
- 元の依頼・受け入れ条件・承認済みの制約を特定する。承認済みの設計は要件と区別する。要件・対象の不明点が構成や評価に影響する場合は質問し、推測で補わない。

## 2. 既存レビューを確認する

同一セッション内のツール実行結果・レビュー結果、およびユーザーが提示した記録を確認する。
「セルフレビューした」「問題なし」という発言だけでは組み込みレビューの実施済み扱いにしない。

再利用には以下の確認が必要。

- 種類・実行方法・完了結果: 組み込みレビュー、要件・設計レビュー、テストを区別する。失敗・中断は完了扱いにしない。
- 対象: リポジトリ、比較方法、比較元の SHA、対象の HEAD / コミット SHA、対象ファイル。
- 作業ツリーの識別情報: staged / unstaged 差分と未追跡の対象ファイルのパス・内容を含むハッシュ。ファイル内容や秘密情報自体は記録に残さない。
- 実行時のモデル・effort と、その確認根拠。記録がなければ「設定不明」とする。
- レビュー後のコード変更、要件・制約の変更、および未解決の指摘。

同じ対象・範囲に対する完了済みレビューで、その後に対象内容や評価に関わる要件の変更がなければ再利用する。
局所レビューをブランチ全体のレビューとして扱わない。指摘が残っている場合は結果を引き継ぎ、解決済みとはみなさない。
変更があれば変更箇所と影響範囲を再レビューする。組み込みコマンドでその範囲を正確に指定できない場合は、適切な全体範囲を再レビューする。
識別情報が不足して同一性を確認できない場合は「履歴確認不能」と明示し、必要なレビューを再実行する。
モデル・effort が低い、異なる、または不明という理由だけで有効な既存レビューを無効にしない。追加レビューを実施する場合は、今回のリスクに対して不足する確認と再実行の理由を説明する。

## 3. 構成を示して実施する

ファイル数・行数だけで判定せず、動作変更の有無、影響範囲、仕様・設計の変更、データや権限への影響で判断する。

| 変更の性質 | 推奨する構成 |
| --- | --- |
| 文言・コメントなど動作に影響しない変更 | 簡易差分確認 |
| 局所的なバグ修正 | 組み込みレビュー |
| 機能追加・仕様変更・リファクタリング | 組み込み → 独立した要件・設計レビュー |
| 認証・認可・決済・データ更新・DB変更など影響の大きい変更 | 組み込み → 独立した要件・設計レビュー ＋ 重点的な検証結果の確認 |

小規模でも設計判断を含む場合は要件・設計レビューを追加する。実施済みの有効なレビューは省略し、残る確認だけを実施する。
新たに実施すべきレビュー・検証がない場合は、判定理由と既存結果・未解決事項を報告して終了する。
簡易差分確認は意図した文言・変更範囲の確認に限定する。動作への影響が判明した場合は構成を見直す。

### モデル・effort の選定

- モデル・effort は `AGENTS.md` の「使用できるモデルと推論レベルの上限」に従う。組み込み・独立レビューとも上限を適用し、ユーザーの明確な指示なく Astra・過去モデルを選択・代用しない。明示された例外は指定された範囲だけに適用し、モデルの指定だけで推論レベルの上限を変更しない。
- メインでの構成判断・結果集約は、推奨提示後にユーザーが選んだ現在のままの続行、または設定変更後の続行に従う。メインの実効モデル・effort や利用可能なモデルを調べず、「現在の設定不明」との報告も行わない。メインセッションや共通設定ファイルを自分で変更しない。
- 組み込み・独立レビュー用の設定は次の表を使い、上限内でモデル名と effort をセットで明示指定する。メインと同じ設定かどうかは調べない。複数の行に該当する場合は表の中で重い設定の行を優先する。ユーザーの明示指定を優先し、利用可否はツールの対応情報や実行結果で判断する。利用不能なら理由と許可範囲の代替設定を示す。

| レビュー | モデル / effort |
| --- | --- |
| メインの構成判断・結果集約、簡易差分確認 | 推奨提示後のユーザーの判断に従う |
| 局所的な修正の組み込みレビュー | `gpt-6.1-sol` / `medium` |
| 機能追加・設計変更・複数箇所に影響する変更の組み込みレビュー、独立した要件・設計レビュー | `gpt-6.1-sol` / `high` |
| 認証・認可・決済・データ更新・DB・マイグレーション・公開 API・並行処理、原因不明・戻しにくい変更、または特に難しいレビュー | `gpt-6.1-sol` / `high`（組み込み・独立レビューとも） |

- 表は通常の推奨値とし、判断に迷って上位の条件を採用する場合も `high` までとする。`xhigh` は、レビュー自体について `high` では不足し、`xhigh` が最適だとする具体的な理由と期待する改善を示せる場合だけ選ぶ。高リスク・原因不明や、メインの設定を理由に選ばない。
- 選定したモデル・effort と、CLI 引数およびサブエージェントの起動パラメータを一致させる。重い独立レビューでも選定した `reasoning_effort` を明示し、モデルの既定値に任せない。
- 第三者視点は履歴を引き継がないことを優先し、別モデルへの変更を必須にしない。重要な設計判断や評価が割れる問題では、追加時間・使用量を考慮して許可範囲の別モデルによる追加レビューを選べる。
- `/review` の `review_model`、別プロセスの `codex review` の設定、サブエージェントの継承・既定値は区別する。メインの設定がすべてに自動適用されると扱わない。

実行前に次の構成をユーザーに示す。メインの推奨設定への判断が未回答、または推奨値が変わる場合は判断を待つ。同一作業で同じ推奨値への判断が済んでいれば、構成だけの承認は改めて求めず続ける。

- 対象範囲、追加指示の解釈・重点観点、規模・リスクの判定とその理由。未コミット・未追跡変更を追加するか不明な場合は、その対象について質問する。
- 再利用するレビューと、その対象・完了根拠。省略できない場合の理由。
- 実施するレビュー、順序、担当、必要なテスト・動作確認。
- 各レビューへ明示指定するモデル・effort・選定理由。メインの現在設定との比較は行わない。再利用するレビューの設定が不明ならその旨も示す。
- 不明点・未確認事項。サブエージェントや組み込みコマンドが利用できない場合の代替案。

レビュー依頼は、提示した構成で読み取り専用のレビューと必要な検証を実施する指示として扱う。コード修正など別の操作への許可には広げない。
実行中に対象やリスクが変わり、構成・範囲の拡大が必要になった場合は、理由と追加作業を示して続ける。対象の解釈が決まらない場合は質問する。
選んだモデル・effort を利用できない場合は、理由と許可範囲の利用可能な代替設定を示して続ける。適切な代替がなければ未実施と報告する。

## 4. レビューを実施する

開始前に対象の識別情報を再確認する。順序は原則として組み込みレビュー → 要件・設計レビュー → 結果の集約とする。

### 組み込みレビュー

- 作業ツリー: `codex review --uncommitted`（staged / unstaged / 未追跡）。
- ベースブランチ比較: `codex review --base <branch>`。
- 単一コミット: `codex review --commit <sha>`。
- 任意の比較範囲: `codex review` のカスタム指示で比較方法と範囲を明示する。`A..B` と `A...B` を勝手に置き換えない。

`--uncommitted`、`--base`、`--commit`、カスタム指示は併用せず、いずれか一つを使う。実行前に利用中の `codex review --help` と照合する。
追加指示を組み込みレビューへ渡す場合は、提示した比較方法・対象範囲と重点指示をまとめたカスタム指示を使用する。要件・設計など担当外の指示は独立レビューへ渡す。組み込みの実際の対象範囲が提示した範囲と一致することを確認し、`<base>...HEAD` に未コミット変更が混ざるなど一致しない場合もカスタム指示で範囲を明示する。
選んだ設定をその実行だけに明示指定する。対応する CLI では `-c 'model="<model>"' -c 'review_model="<model>"' -c 'model_reasoning_effort="<effort>"'` を付け、既存の `review_model` による意図しないモデル選択も避ける。モデル・effort の指定を自然言語の指示だけで代用しない。
カスタム指示は構造化引数または stdin で安全に渡す。このスキルを再起動せず、組み込みのレビューだけを実施するよう指定する。
コマンドの完了と出力を確認する。利用不能・失敗時は未実施と報告し、メインエージェントのレビューで黙って代用しない。代替構成を実施できる場合は変更を示して続ける。

### 独立した要件・設計レビュー

この工程ではサブエージェントへ委譲する。親の会話履歴を継承しない新規コンテキストで起動する（`fork_turns="none"` が使える環境ではそれを指定）。
選んだモデル・effort を起動パラメータで明示指定する（対応する環境では `model` / `reasoning_effort`）。カスタムエージェント設定による上書きも確認し、親からの継承や既定値に任せない。指定できない環境では、解決される設定が許可範囲内と確認できる場合だけ実施する。設定を確認できなければ、その制約と未実施を報告する。

- 渡す情報: ユーザーの要件・受け入れ条件、担当範囲に関わるユーザーの追加指示と確定した解釈、承認済みの制約、要件と区別した設計、リポジトリと対象範囲・識別情報、適用される `AGENTS.md`、関連資料の場所。重点指示は確認の優先度として扱い、問題の存在や結論を前提にしない。
- 渡さない情報: 実装担当の評価・自己正当化、既存レビューの結論、メインエージェントが付け加えた誘導的な懸念や期待する回答。元の要件・追加指示をメインエージェントの解釈だけに置き換えない。
- 担当範囲: 要件の不足・逸脱、要件外の変更、設計の妥当性と既存設計との整合性、不要な抽象化・冗長さ、命名・保守性。
- コードと関連実装を自ら調査し、根拠付きの指摘・修正案・要確認事項を返すよう依頼する。独自の不具合・セキュリティチェックや `my-review` の再起動は依頼しない。
- 読み取り専用の作業とし、修正・追加エージェントの起動は行わせない。スコープ外でも重大な問題に気づいた場合は根拠とともに報告する。

結果を待ってから集約する。新規コンテキストでの委譲ができなければ、その制約を説明し、実施可能な代替案があれば構成変更を示して続ける。
メインエージェントは指摘の根拠を確認し、採否を説明する。実装時の方針と違うことだけを理由に却下しない。

## 5. 結果を報告する

- findings を先に、重要度順に提示する。指摘には `#1` からの一意の番号を付け、後続の相談・再レビューでも維持する。追加指摘は未使用の番号を使う。
- 組み込みと要件・設計レビューの重複指摘は集約し、出典・重要度・ファイルと行・問題・影響・修正案を示す。
- 指摘がない場合は「指摘なし」とし、確認できた範囲と残る不明点・検証不足を記載する。指摘がないことを全観点の安全保証や未実行テストの成功に置き換えない。
- 「コード上で確認」「テスト・実行結果で確認」「未確認」を区別する。
- 実施／再利用／未実施のレビューと理由、検証結果、次のアクションを記載する。
- 次回の重複防止のため、各レビューの種類・実行方法・モデル・effort・完了状態・対象識別情報・要件の参照元・結果を会話内に記録する。モデル・effort は指定値と、実行情報で確認できた実効値を区別し、確認不能な値を確認済みとしない。終了時にも対象を確認し、実行中の変更があれば結果が適用できる範囲を明示する。

レビュー依頼にはコード修正・commit・push・PR 作成を含めない。修正はユーザーの許可を得てから行う。
