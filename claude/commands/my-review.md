現在の修正内容をテックリード視点でレビューする。
規模とリスクを判定し、組み込みレビュー（`/code-review` / `/security-review` / `/simplify`）との組み合わせを提案して、承認後に実行する。

## 引数

引数: `$ARGUMENTS`

引数は、形式にかかわらず必ず文章として受け取り、意図を解釈する。
git の revision（例: `HEAD~1`, `main..feature/xxx`）が渡された場合も、重点的に見たい範囲・観点の指定（例: 「認可まわりを重点的に」「claude 関連のファイルに限定して」）が渡された場合も、まず文章として読み、後続の `git diff` やサブエージェントへの指示にどう渡すかを判断する。
解釈結果は手順 5 の提案に表示する。解釈に迷う場合は、推測せず、手順 5 の提案より前に `AskUserQuestion` で確認する。
引数全文を `git` やシェルに直接渡さない。解釈した ref・パスだけを、必要に応じてクォートして渡す。

* 引数なし: base との差分（ブランチのコミット済み変更 + 未コミットの変更）を対象にする。比較範囲は `--merge-base <base>`（Git 2.30 以降が必要）
  * base は次の順に試し、最初に成功したものを使う: `git symbolic-ref -q --short refs/remotes/origin/HEAD`、`main`、`master`（`git show-ref -q --verify refs/heads/<名前>`）。すべて失敗したらユーザーに確認する
  * main / master 上で base と同じ位置にあるときは、作業ツリーの差分だけになる。base が origin/HEAD の場合は、未 push のコミットがあれば、それも含まれる
* 引数あり: 次の 3 要素に解釈する。複数を含んでもよい。含まれない要素は、引数なしの既定を使う
  * **比較範囲**: 意図に合う `git diff` の形を選ぶ。ref は `git rev-parse --verify -q <ref>^{commit}` で存在を確認する
    * 「main との差分」、単一 ref（`main`, `HEAD~1` など）→ `--merge-base <ref>`（未コミットの変更を含む）
    * 「未コミットのみ」→ `HEAD`
    * 「直前のコミット」→ `HEAD~1 HEAD`（`HEAD~1` が存在しない初回コミットは、空ツリー `$(git hash-object -t tree /dev/null)` と `HEAD` の比較。マージコミットは第 1 親との差分になる）
    * `A..B`、`A...B` → コミット間の比較
    * 2 つのコミットを直接比べる形（`HEAD~1 HEAD`、`A..B`、`A...B`、初回コミット）では、`--merge-base` は範囲指定と併用できないため使わない。未追跡ファイルと simplify は対象外とする
  * **絞り込み**: 対象パスや除外（例: 「codex は除く」）。`-- <パス>` と pathspec（例: `':(exclude)codex'`）で表す
  * **重点観点**: 重点的に確認したい観点・領域。本体の観点とサブエージェントへの指示に反映する（他の観点も省略しない）

比較範囲と絞り込み（パス）を合わせて「対象範囲」と呼ぶ。以降の git コマンドは `git diff [オプション] <比較範囲> [-- <パス>]` の形で実行する（オプションは必ず先に書く）。ファイル名を出力する git コマンド（`--name-only`、`ls-files`）には `-c core.quotepath=false` を付ける（日本語名などが引用符付きの表記になるのを防ぐ）。

## 役割分担

重複を避けるため、観点ごとに担当を分ける。

| 観点 | 担当 |
|---|---|
| 要件適合 | my-review 本体 |
| 互換性・影響範囲（既存仕様・破壊的変更） | my-review 本体 |
| 既存実装との整合性 | my-review 本体 |
| 命名・可読性 | my-review 本体 |
| 検証可能性（テスト・ログ・実行結果で動作を確認できるか） | my-review 本体 |
| バグ・エッジケース | `/code-review` |
| セキュリティ | `/security-review` |
| 冗長・再利用・効率 | `/simplify` |

my-review 本体では、バグ・エッジケース・セキュリティ・冗長性を能動的に探さない。
diff を読む中で明らかな問題に気づいた場合のみ、指摘に含める。

## 手順

### 1. diff を取得する

1. リポジトリルートで実行する。`git status --short --branch` で現在のブランチと作業ツリー状態を確認する。
2. `git diff <比較範囲> [-- <パス>]` で対象範囲の diff を取得する。

未追跡ファイルは `git diff` に出ない。`git ls-files --others --exclude-standard [-- <パス>]` で一覧する（コミット間比較のときは対象外）。ある場合は、diff が空でも終了せず、手順 5 で対象に含めるか確認する。

diff が空で、未追跡ファイルもない場合は、終了前に以下を確認する。想定と違う場合は、ユーザーに確認する。

* `git status` の出力（ブランチ、未追跡ファイル、upstream との差分）が想定どおりか。
* base が正しく決まっているか。
* `git log --oneline --decorate -5` で直近コミットが想定どおりか。
* コミット済みの変更を見たい場合は、比較範囲の指定（例: 「直前のコミット」）を案内する（main / master 上で base と同じ位置にあるときは、作業ツリーの差分だけが対象になる）。

上記を確認しても diff が空で、未追跡ファイルもない場合のみ「変更なし」と報告して終了する。

### 2. diff を確認する

* diff の内容を確認する。未追跡ファイルを対象に含める場合は、その内容も読む。
* レビューに必要な情報が diff だけでは不足する場合は、関連する Controller / Service / Request / Policy / Model / Migration / Test なども調査する。重点観点がある場合は、その領域の関連コードも調査する。
* 既存ヘルパーとの重複（simplify 要否の判定材料）も、この調査で確認する。

### 3. 規模とリスクを判定する

`git diff --stat <比較範囲> [-- <パス>]` で、変更ファイル数と追加・削除行数を確認する。

未追跡ファイルは `--stat` に出ない。ある場合は含める前提で、ファイル数と `wc -l` の行数を加算して判定する。手順 5 で除外されても構成は変更しない（承認された構成で実施する）。除外の結果、対象が空になる場合は「変更なし」と報告して終了する。

**規模**（目安。内容に応じて調整し、根拠を提案に書く）

行数は追加と削除の合計。

| 規模 | 目安 |
|---|---|
| S | 3 ファイル以下 かつ 50 行以下 かつ ロジック変更なし（設定・ドキュメント・リネームなど） |
| L | 10 ファイル以上、または 300 行以上、または複数レイヤーにまたがる変更・Migration を含む |
| M | 上記以外 |

**リスクフラグ**（該当するものを挙げる）

* 認証・認可（Policy / Middleware / Gate / ロール）
* 入力受付（Request / Controller / フォーム）
* 外部通信（HTTP クライアント / Webhook / コマンド実行）
* 秘密情報・認証情報の追加・変更、ログ出力
* DB（Migration / 生 SQL）

**simplify 要否のシグナル**（未コミットの変更で判定する。1 つでも該当すれば提案し、実施は個別承認）

* 新規追加コードが多い
* 類似処理が重複している
* 既存ヘルパーと機能が重複している
* 不要な抽象化・過剰な分岐がある

simplify は推奨構成に含めず、書き換え可能なファイルがあり、かつシグナルがあるときだけ別途提案する。書き換え可能なファイルは、未コミットの変更があるファイル（`git -c core.quotepath=false diff --name-only --diff-filter=d HEAD [-- <パス>]` の結果と、質問 4 で含めた未追跡ファイル）のうち、絞り込みのパス内のものに限る。未追跡ファイルを含めた場合のみ候補になるファイルがあるなら、提案でその旨を示す。コミット間比較のときは提案しない。

**推奨構成**

| 条件 | 構成 |
|---|---|
| S | my-review 本体のみ |
| M | 本体 + `/code-review medium` |
| L | 本体 + `/code-review high`。`/code-review ultra` も案内する |
| リスクフラグあり（規模問わず） | 上記に `/security-review` を追加 |

`/code-review ultra` はユーザー操作でのみ起動できる。自分では起動せず、「ultra を推奨。ご自身で実行を」と案内するだけにする。

**モデル**（提案表に表示する。ユーザーは変更できる）

| レビュー | モデル |
|---|---|
| my-review 本体 | メインのまま |
| `/code-review`（S・M） | 継承（`model` を省略） |
| `/code-review`（L） | `opus` を提案。メインが opus 以上のときは継承 |
| `/security-review` | `opus` を提案。メインが opus 以上のときは継承 |
| `/simplify` | 継承 |

* haiku はレビューに使わない。
* effort は Agent ツールで指定できない。起動したモデルの設定で決まる。`model` を省略すれば（既定のサブエージェントモデルが設定されていなければ）メインと同じモデルなので、同じ値になる。別のモデルを指定すると、そのモデルの `modelSettings` の値になる（なければモデルの既定とみられる）。
* 実測（この環境）: 独立したプロセスで `modelSettings` に opus の `high` を指定すると、メインも `model: opus` のサブエージェントも high だった（指定なしは medium）。一方、セッション起動後に追記した設定は、実行中のセッションに反映されなかった。別モデルを提案するときは、提案表の「モデル」列に effort（`modelSettings` の値、なければモデルの既定。例: `opus（effort: high）`）を併記し、継承（メインと同じ effort）との比較をユーザーが選べるようにする。

### 4. 実施済みレビューを確認する

同一会話内で、サブエージェント等により code-review / security-review / simplify 相当のレビューが既に実施されていないか、会話履歴から確認する。my-review 本体は毎回実施するため対象外。

1. 実施済みのレビューについて、種別・対象ファイル・範囲・レベル・重点観点を特定する。
2. 今回の推奨より軽い（範囲が狭い、レベルが低い）場合、または重点観点が前回と異なる場合は、実施済みとみなさない。
3. 実施以降に変更されたファイルと突き合わせる。Edit / Write に加え、Bash による変更や手動編集も考慮する。
   * 変更なし: スキップする。前回の指摘は番号を維持して今回の報告に取り込む。
   * 変更あり: 変更されたファイルのみ再実施する。
   * 判別できない（別セッションで実施、コンテキスト圧縮で履歴が不明、Bash や手動編集の有無が不明など）: 推測せず、手順 5 でユーザーに確認する。

### 5. 構成を提案し、承認を得る

まず判定結果を以下の形式で提示する（値は例）。

```text
## レビュー構成の提案

**対象範囲**: 比較範囲 `--merge-base origin/master` / 絞り込み `claude/`（`codex` を除外）
**重点観点**: 認可まわり（引数より） / なし
**規模**: M（5 ファイル / +120 -30、ロジック変更あり）
**リスクフラグ**: 認可（PolicyX の変更）
**未追跡ファイル**: あり（N 件。対象に含めるか確認） / なし
**simplify**: 提案（理由） / 不要

| レビュー | 推奨 | モデル | 状態 |
|---|---|---|---|
| my-review 本体 | ○ | メイン | 実施 |
| /code-review medium | ○ | 継承 | 実施済み（3 ファイル変更あり）→ 変更ファイルのみ再実施 |
| /security-review | ○ | opus（effort: high） | 実施済み（変更なし）→ スキップ |
| /code-review ultra | △ | - | ユーザー操作で実行（L のみ） |
| /simplify | △ | 継承 | 未実施（個別承認。変更ファイルの再実施を含む） |

○ = 推奨 / △ = 任意・案内
```

続けて `AskUserQuestion` で最終判断を求める。1 回の呼び出しは最大 4 問、各問の選択肢は 2〜4 個に収める。

1. **構成**（単一選択）: 推奨構成で実施 / 軽くする / 重くする / 中止
   * 規模 S の場合は「軽くする」を、追加できるレビューが残っていない場合は「重くする」を出さない。
   * 「軽くする」「重くする」が選ばれた場合は、別の呼び出しで、実施するレビューを `multiSelect` で確認する（選択肢は 4 個以内。候補はレビューの種別とし、レベルの変更は「Other」で指示してもらう。候補が 1 つのときは 実施する / しない の単一選択にする）。構成が変わったら、最終構成に対して手順 4 の判定をやり直す（やり直しで新たに判別不能なレビューが出た場合は、質問 3 を再度行う）。
   * 「中止」は、何も実行せず終了する。
   * 対象範囲・重点観点の解釈やモデルが違う場合は「Other」に自由記述して修正できる旨を、質問文に添える。修正があれば、同じ呼び出しの質問 2〜4 の回答を破棄する。対象範囲が変わった場合は手順 1〜4 からやり直し、重点観点・モデルだけの変更は解釈をやり直して、提案を再提示したうえで、質問し直す。
2. **simplify**（提案する場合のみ。実施する / 実施しない）: ファイルを書き換える旨と、「変更されたファイルは、最終構成に含まれるレビューを再実施する」旨を明記する。この再実施は simplify の承認に含まれる。ユーザーが外したレビューは再実施しない。
3. **判別不能なレビュー**（手順 4 で該当がある場合のみ）: 1 件なら 再実施 / スキップ の単一選択、2 件以上なら `multiSelect` で再実施するものを選ばせる。選ばれなかったものはスキップする。質問 1 のフォローアップ結果と食い違う場合は、後から選ばれたフォローアップを優先する。
4. **未追跡ファイル**（ある場合のみ。含める / 含めない）

承認を得るまでレビューを実行しない。

### 6. レビューを実行する

組み込みレビューは `general-purpose` サブエージェントで実行する。モデルは提案表のとおりに指定する（継承の場合は `model` を省略する）。

レビュー用の一時ファイル（simplify 実行前の保存、diff ファイル）は、スクラッチパッドに保存する（指定がない環境では `mktemp -d` で作る）。秘密情報が入り得るため、削除する。diff ファイルは手順 7 の突き合わせ後に削除する。simplify 実行前の保存は、報告後にユーザーが戻す・戻さないを決めるまで残し、決まったら削除する。

1. **simplify**（質問 2 で承認された場合のみ）
   * 実行前に、書き換え可能なファイル（手順 3）を、パスを保ったままスクラッチパッドへコピーして保存する（`cp --parents` など）。集合が空なら、simplify をスキップして、その旨を報告する。あわせて、未コミットの変更がある全ファイル（`git -c core.quotepath=false diff --name-only -z HEAD` と `git ls-files -o --exclude-standard`）の SHA-256 一覧と、`git status --short -uall` の結果を保存する。
   * サブエージェントには、書き換え可能なファイルの一覧を指示文で渡し、それ以外の変更と、ファイルの新規作成・削除は禁止する。diff ファイルは、この時点ではまだ無いので渡さない。結果は、変更したファイルの一覧と要約で返させる。
   * ファイルを書き換えるため、他のレビューより先に単独で実行する。Skill がバックグラウンド実行を返した場合も、完了を待ってから次に進む（待機ルールは下記）。未完了のときは、再実施せず、保存したコピーとの比較で状態を確認し、手順 6-2 に進むか中止するかをユーザーに確認する。
   * 完了後、保存したコピーと現在のファイルの比較、SHA-256 一覧の再計算、`git status --short -uall` の差分から、simplify が変更・新規作成・削除したファイルを特定し、報告用に控える。書き換え可能なファイル以外の変更や、禁止した新規作成・削除があれば、違反として報告する。ユーザーが戻したい場合は保存したコピーを基に案内し、勝手に戻さない。
   * simplify が変更したファイルは、質問 2 のとおり、手順 4 で実施済み・変更なしと判定していても、最終構成のレビューを再実施する。
2. **レビュー対象の diff ファイルを作る**（simplify を実施した場合は、実施後の最新の状態で）
   * `git diff <比較範囲> [-- <パス>]` の出力を保存する。未追跡ファイルを対象に含める場合は、`git diff --no-index -- /dev/null <ファイル> || true` の出力を追記する（ファイルはリポジトリルートからの相対パスで渡す。絶対パスだと diff のヘッダが崩れる。バイナリは除外し、その旨を注記する）。
   * 変更ファイルのみ再実施するレビューには、`git diff <比較範囲> -- <対象ファイル>`（対象に含める未追跡ファイルは、上と同じ `--no-index` の出力）を、レビューごとの別ファイルとして保存する。対象ファイルは、（手順 4 で変更ありと判定されたファイル ∪ simplify が変更したファイル）∩ 絞り込みパス。simplify を実施した場合は、手順 4 でスキップと判定したレビューも含む。質問 3 で「スキップ」が選ばれたレビューと、ユーザーが外したレビューは対象外。
   * 突き合わせは、レビューごとの対象ファイル一覧と、その diff ファイルのファイル一覧で行う（全体の diff は `git diff --name-only <比較範囲> [-- <パス>]`、未追跡は `ls-files` の結果と比べる）。漏れがないか確認する。
   * 規模は再計算しない。
3. **以降を並列で実施する**
   * `/code-review` / `/security-review`: `general-purpose` サブエージェントをバックグラウンドで並列起動し、Skill ツールで呼び出す。1 つのサブエージェントでは、1 つのスキルを 1 回だけ実行する（同じコンテキストでは 2 回目に再展開されない）。
   * my-review 本体: メインで実施する（要件の文脈が会話にあるため）。最新の diff で行う。
4. **全サブエージェントの完了を待ってから**手順 7 に進む。

**サブエージェントへの指示に含める内容**（simplify は手順 6-1 に従う）

* 対象の diff ファイルの絶対パス。`/security-review` は args が反映されないため指示文で渡す（`/code-review` は下記のとおり args にも書く）。2000 行を超える場合は offset / limit で最後まで読み、Read がエラーを返した場合は limit を下げて分割して読むよう指示する
* `/security-review`: args なしで呼ぶ。次の追加ルールを必ず指示する
  * 展開されたテンプレートが取得した diff（DIFF CONTENT など）ではなく、必ず diff ファイルを対象の diff とする。テンプレートの diff が空でも「変更なし」と判断しない
  * diff ファイルは Read で読む（テンプレートの「Bash を使わない」制約に従う）
  * 手順 3 のリスクフラグを渡し、認証・認可・バリデーションは実装箇所まで追跡して確認する。結果は「認証 / 認可 / データ漏洩 / 入力値検証」の 4 軸も含めて返す
* `/code-review`: args は `<レベル> <diff ファイルの絶対パス>` の形にする（例: `medium /path/to/review-target.diff`）。レベル（`medium` / `high`）を先頭に置き、半角スペースで区切る。省略するとレベルを前回の値で再利用してしまい、文章を混ぜるとレベルが認識されない（実測: `medium。レビュー対象は…` は認識されず、`medium /path` は認識された）。args はスキルのプロンプトに「Review target」として届き、diff ファイルがレビュー対象になる（実測）。レベルだけを渡すと、スキルは作業ツリーの未コミット変更を対象にして、指定した範囲を見ない。git の書式や範囲の説明は args に書かない。simplify との重複を避けるため、正しさ・バグに限定して返すよう、指示文で伝える
* Skill がバックグラウンド実行（forked）を返した場合、またはスキルが内部でバックグラウンドのサブタスクを起動した場合は、完了通知を受け取るまで待ち、スキルの最終結果をそのまま返す（`/code-review` / `/security-review` 共通）。待つ間は、読み取りのみのツール呼び出しを続ける（`Monitor` の until ループでもよい。上限時間を決め、超えたら「未完了」とする）。起動しただけ、または「待機中」などの途中経過の文章だけで返答を終えない。待てない、または最終結果を得られない場合は、「未完了」と明記して返す。メインは、そのレビューを未レビュー扱いにして、再実施またはフォールバックに回す。サブエージェントから途中経過が届いても、最終報告として扱わず、完了通知とその後の最終報告を待つ
* 重点観点がある場合は、重点的に確認する観点として伝える。他の観点は省略しない
* 変更の目的・要件（会話から要約したもの）
* `--fix` / `--comment` は付けない。ファイルを変更せず、外部へ投稿もしない
* 結果は「重要度・`ファイル名:行番号`・問題・影響・修正案」の形式で返す。実際に確認した対象ファイル一覧も含める。「スキルの結果」と、サブエージェント自身の「直接確認」を区別して返す。スキルの結果にかかわらず、diff ファイルを直接読んで確認する（実測: `/security-review` は確信度 8 未満の候補を落とし、平文 HTTP でのトークン送信のような実害のある指摘が 0 件になった。除外された候補も併記する）
* Skill ツールが使えない、またはサブエージェントが失敗した場合は、同等の観点を直接指示してレビューさせる。その旨を「実施したレビュー」に明記する。モデルや範囲が承認した構成から変わる場合は、実行前に再承認を取る

サブエージェントの結果は、手順 7 の「実施したレビュー」（エージェント名・モデル・委譲内容・概要）に集約して報告する。

**my-review 本体の観点**

* **要件適合**: 変更が意図した目的を正確に達成しているか。要件が会話から分からない場合は「要確認」とする
* **互換性・影響範囲**: 既存仕様・API 契約・データへの影響、破壊的変更、呼び出し元・依存先への波及がないか
* **既存実装との整合性**: 既存の設計・規約・命名規則と整合しているか
* **命名・可読性**: 変数名・関数名が意図を正確に表しているか。将来の保守性を損なわないか
* **検証可能性**: テスト・ログ・実行結果などで動作を確認できるか。テストの有無・不足を確認する

重点観点がある場合は、その観点を優先して深く確認する。

### 7. 統合して報告する

* 本体とサブエージェントの指摘を一本化し、重複する指摘はマージして由来（`my-review` / `code-review` / `security-review` / `前回レビュー`）を併記する。
* サブエージェントが報告した対象ファイル一覧を、diff ファイルのファイル一覧と突き合わせる。漏れがあれば、再実施するか、未レビューとして明記する。突き合わせの後に、diff ファイルを削除する。
* simplify を実施した場合は、報告に、保存したコピーの場所と戻し方を含め、戻す・戻さないをユーザーに確認する。決まったら、保存したコピーを削除する。
* 番号付け:
  * 初回は、重要度順に `#1` から始まる一意の連番を振る。
  * 同一会話に既存の `#N` がある場合は、その番号を維持する。新規の指摘は最大番号の次から振り、末尾に追記する。
  * 前回の指摘と同一の問題（同じファイル・同じ原因なら、行番号が動いても同一とする）には、既存の番号を使う。
  * 変更により解消した前回の指摘は、番号を残して「解消済み」と記す。欠番にせず、再採番しない。
* 未実施のレビューは総評に明記する。
  * `/security-review` を実施しなかった場合: 「セキュリティ未レビュー」（リスクフラグがあるときは特に明記する）
  * `/code-review` を実施しなかった場合: 「バグ・エッジケース未レビュー」
  * `/simplify` を実施しなかった場合: 「冗長・再利用・効率は未レビュー」

## 注意事項

* diff のみで「問題なし」と判断しない
* 推測で判断せず、不明な点は「要確認」とする
* 修正の相談・確認など後続のやり取りでも同じ番号を維持し、再採番しない
* ユーザーの承認なしにレビューを実行しない（手順 5）
* 修正案は提示するが、実際の修正（simplify を含む）はユーザーの許可を得てから行う
