現在の修正内容をテックリード視点でレビューする。
規模とリスクを判定し、組み込みレビュー（`/code-review` / `/security-review` / `/simplify`）との組み合わせを提案して、承認後に実行する。

## 引数

引数: `$ARGUMENTS`

引数は、形式にかかわらず必ず文章として受け取り、意図を解釈する。git の revision（例: `HEAD~1`）も、重点的に見たい範囲・観点の指定（例: 「認可まわりを重点的に」）も、まず文章として読み、後続の `git diff` やサブエージェントへの指示にどう渡すかを判断する。
解釈結果は手順 5 の提案に表示する。迷う場合は、推測せず、手順 5 より前に `AskUserQuestion` で確認する。引数全文を `git` やシェルに直接渡さない。解釈した ref・パスだけを、必要に応じてクォートして渡す。

* 引数なし: base との差分（ブランチのコミット済み変更 + 未コミットの変更）。比較範囲は `--merge-base <base>`（Git 2.30 以降）
  * base は次の順に試し、最初に成功したものを使う: `git symbolic-ref -q --short refs/remotes/origin/HEAD`、`main`、`master`（それぞれ、ローカルは `git show-ref -q --verify refs/heads/<名前>` で確認して `<名前>` を、なければ `git show-ref -q --verify refs/remotes/origin/<名前>` で確認して `origin/<名前>` を base とする）。すべて失敗したらユーザーに確認する
  * main / master 上で base と同じ位置にあるときは、作業ツリーの差分だけになる。base が origin 系（`origin/HEAD`、`origin/<名前>`）の場合は、未 push のコミットも含まれる
* 引数あり: 次の 3 要素に解釈する（複数可。無い要素は引数なしの既定）
  * **比較範囲**: ref は `git rev-parse --verify -q <ref>^{commit}` で存在を確認する
    * 「main との差分」、単一 ref（`main`, `HEAD~1`）→ `--merge-base <ref>`（未コミットを含む）
    * 「未コミットのみ」→ `HEAD`
    * 「直前のコミット」→ `HEAD~1 HEAD`（初回コミットは空ツリー `$(git hash-object -t tree /dev/null)` と `HEAD`。マージコミットは第 1 親との差分）
    * `A..B`、`A...B` → コミット間の比較
    * 2 つのコミットを直接比べる形では、`--merge-base` を使わず（範囲指定と併用できない）、未追跡ファイルと simplify は対象外とする
  * **絞り込み**: 対象パスや除外（例: 「codex は除く」）。`-- <パス>` と pathspec（例: `':(exclude)codex'`）で表す
  * **重点観点**: 重点的に確認したい観点・領域。本体の観点とサブエージェントへの指示に反映する（他の観点も省略しない）

比較範囲と絞り込み（パス）を合わせて「対象範囲」と呼ぶ。以降の git コマンドは、すべてリポジトリルートで実行し（`git ls-files -o` や `cp --parents` は、実行ディレクトリ配下だけが対象になるため）、diff は `git diff [オプション] <比較範囲> [-- <パス>]` の形にする（オプションは先に書く）。ファイル名を出力するコマンド（`--name-only`、`--name-status`、`ls-files`）と、手順 6-2 で diff ファイルを作る `git diff` には `-c core.quotepath=false` を付ける。

## 役割分担

重複を避けるため、観点ごとに担当を分ける。

| 観点 | 担当 |
|---|---|
| 要件適合 | my-review 本体 |
| 互換性・影響範囲（既存仕様・破壊的変更） | my-review 本体 |
| 既存実装との整合性 | my-review 本体 |
| 命名・可読性 | my-review 本体 |
| 検証可能性（テスト・ログ・実行結果で動作を確認できるか） | my-review 本体 |
| バグ・エッジケース | `/code-review` |
| セキュリティ | `/security-review` |
| 冗長・再利用・効率 | `/simplify` |

my-review 本体では、バグ・エッジケース・セキュリティ・冗長性を能動的に探さない。diff を読む中で明らかな問題に気づいた場合のみ、指摘に含める。

## 手順

### 1. diff を取得する

1. リポジトリルートで `git status --short --branch` を実行し、ブランチと作業ツリーの状態を確認する。
2. `git diff <比較範囲> [-- <パス>]` で対象範囲の diff を取得する。
3. 未追跡ファイルは `git diff` に出ない。`git ls-files --others --exclude-standard [-- <パス>]` で一覧する（コミット間比較は対象外）。ある場合は、diff が空でも終了せず、手順 5 で対象に含めるか確認する。

diff も未追跡ファイルも空なら、終了前に確認する: `git status` の出力、base の決定、`git log --oneline --decorate -5`。想定と違えばユーザーに確認する。コミット済みの変更を見たい場合は、比較範囲の指定（例: 「直前のコミット」）を案内する。問題なければ「変更なし」と報告して終了する。

### 2. diff を確認する

diff（対象に含める未追跡ファイルを含む）を読む。不足する情報（関連する Controller / Service / Request / Policy / Model / Migration / Test、重点観点の領域、既存ヘルパーとの重複）は、関連コードを調査して補う。

### 3. 規模とリスクを判定する

`git diff --stat <比較範囲> [-- <パス>]` で、ファイル数と追加・削除行数（合計）を確認する。未追跡ファイルは `--stat` に出ないので、含める前提でファイル数と `wc -l` の行数を加算する。手順 5 で除外されても構成は変えない。対象が空になる場合は「変更なし」で終了する。

**規模**（目安。根拠を提案に書く）

| 規模 | 目安 |
|---|---|
| S | 3 ファイル以下 かつ 50 行以下 かつ ロジック変更なし（設定・ドキュメント・リネームなど） |
| L | 10 ファイル以上、または 300 行以上、または複数レイヤーにまたがる変更・Migration を含む |
| M | 上記以外 |

**リスクフラグ**: 認証・認可（Policy / Middleware / Gate / ロール）、入力受付（Request / Controller / フォーム）、外部通信（HTTP クライアント / Webhook / コマンド実行）、秘密情報・認証情報の追加・変更・ログ出力、DB（Migration / 生 SQL）。該当するものを挙げる。

**simplify**: 未コミットの変更で次のシグナルが 1 つでもあれば提案する（新規追加が多い、類似処理の重複、既存ヘルパーとの重複、不要な抽象化・過剰な分岐）。推奨構成には含めず、書き換え可能なファイルがあるときだけ別途提案し、実施は個別承認とする。書き換え可能なファイルは、未コミットの変更があるファイル（`git -c core.quotepath=false diff --name-only --diff-filter=d HEAD [-- <パス>]` の結果と、質問 3 で含めた未追跡ファイル）のうち、絞り込みパス内のものに限る。未追跡ファイルを含めた場合のみ候補になるファイルがあるなら、提案でその旨を示す。コミット間比較のときは提案しない。

**推奨構成**

| 条件 | 構成 |
|---|---|
| S | my-review 本体のみ |
| M | 本体 + `/code-review medium` |
| L | 本体 + `/code-review high`。`/code-review ultra` も案内する |
| リスクフラグあり（規模問わず） | 上記に `/security-review` を追加 |

`/code-review ultra` はユーザー操作でのみ起動できる。自分では起動せず、「ultra を推奨。ご自身で実行を」と案内するだけにする。

**モデル**（提案表に表示する。ユーザーは変更できる）

| レビュー | モデル |
|---|---|
| my-review 本体 | メインのまま |
| `/code-review`（S・M） | 継承（`model` を省略） |
| `/code-review`（L） | `opus` を提案。メインが opus 以上のときは継承 |
| `/security-review` | `opus` を提案。メインが opus 以上のときは継承 |
| `/simplify` | 継承 |

* haiku はレビューに使わない。
* effort は Agent ツールで指定できず、起動したモデルの設定で決まる。`model` を省略すれば、既定のサブエージェントモデルが未設定の場合に限り、メインと同じモデル・同じ値になる（設定がある場合は、提案表に実際のモデルを明記する）。別のモデルは、そのモデルの `modelSettings` の値（なければモデルの既定）になる。設定の変更は、起動済みのセッションに反映されないことがある。別モデルを提案するときは、提案表の「モデル」列に effort を併記する（例: `opus（effort: high）`）。

### 4. 実施済みレビューを確認する

同一会話内で、code-review / security-review / simplify 相当のレビューが既に実施されていないか、会話履歴から確認する（本体は毎回実施する）。

1. 種別・対象ファイル・範囲・レベル・重点観点を特定する。
2. 今回の推奨より軽い（範囲が狭い、レベルが低い）場合、または重点観点が違う場合は、実施済みとみなさない。
3. 実施以降に変更されたファイル（Edit / Write、Bash、手動編集）と突き合わせる。
   * 変更なし: スキップする。前回の指摘は番号を維持して取り込む。
   * 変更あり: 変更されたファイルのみ再実施する。
   * 判別できない（別セッション、履歴の圧縮、Bash や手動編集の有無が不明など）: 実施済みとみなさず、全範囲で再実施する。提案の状態欄に「履歴確認不能 → 再実施」と書く。

### 5. 構成を提案し、承認を得る

まず判定結果を以下の形式で提示する（値は例）。

```text
## レビュー構成の提案

**対象範囲**: 比較範囲 `--merge-base origin/master` / 絞り込み `claude/`（`codex` を除外）
**重点観点**: 認可まわり（引数より） / なし
**規模**: M（5 ファイル / +120 -30、ロジック変更あり）
**リスクフラグ**: 認可（PolicyX の変更）
**未追跡ファイル**: あり（N 件。対象に含めるか確認） / なし
**simplify**: 提案（理由） / 不要

| レビュー | 推奨 | モデル | 状態 |
|---|---|---|---|
| my-review 本体 | ○ | メイン | 実施 |
| /code-review medium | ○ | 継承 | 実施済み（3 ファイル変更あり）→ 変更ファイルのみ再実施 |
| /security-review | ○ | opus（effort: high） | 実施済み（変更なし）→ スキップ |
| /code-review ultra | △ | - | ユーザー操作で実行（L のみ） |
| /simplify | △ | 継承 | 未実施（個別承認。変更ファイルの再実施を含む） |

○ = 推奨 / △ = 任意・案内
```

続けて `AskUserQuestion` で最終判断を求める。1 回は最大 4 問、各問の選択肢は 2〜4 個。

1. **構成**（単一選択）: 推奨構成で実施 / 軽くする / 重くする / 中止
   * 規模 S では「軽くする」を、追加できるレビューが残っていなければ「重くする」を出さない。
   * 「軽くする」「重くする」は、別の呼び出しで、実施するレビューを `multiSelect` で確認する（選択肢は 4 個以内でレビューの種別。レベルの変更は「Other」。候補が 1 つなら 実施する / しない）。構成が変わったら、手順 4 の判定をやり直す。
   * 「中止」は、何も実行せず終了する。
   * 質問文に、対象範囲・重点観点・モデル・レビューレベル（例: `/code-review` を high に）を変えたい場合は「Other」で修正できる旨を添える。修正があれば、同じ呼び出しの質問 2・3 の回答を破棄する。対象範囲が変わった場合は手順 1〜4 からやり直し、重点観点・モデル・レベルだけなら、解釈と推奨構成を更新し、手順 4 の判定をやり直して、提案を再提示して質問し直す。「Other」で指定したレベル・モデル・重点観点は、やり直し後も保持する。
   * 指定できる `/code-review` のレベルは `low` / `medium` / `high` / `max`。`ultra` は起動せず、手順 3 の案内にとどめる。構成に含まれないレビューへのレベル指定は、そのレビューを追加するかを確認する。レベルを変えても、モデルは規模基準のままにする（変えたい場合はモデルも「Other」で指示してもらう）。
2. **simplify**（提案する場合のみ。実施する / しない）: ファイルを書き換える旨と、「変更されたファイルは、最終構成のレビューを再実施する」旨を明記する。この再実施は simplify の承認に含まれる。ユーザーが外したレビューは再実施しない。
3. **未追跡ファイル**（ある場合のみ。含める / 含めない）。「含めない」で対象が空になる場合は、「変更なし」と報告して終了する

承認を得るまでレビューを実行しない。

### 6. レビューを実行する

組み込みレビューは `general-purpose` サブエージェントで実行する。モデルは提案表のとおりに指定する（継承の場合は `model` を省略する）。

一時ファイル（simplify 実行前の保存、diff ファイル）は、スクラッチパッドに保存する（なければ `mktemp -d`）。秘密情報が入り得るため、diff ファイルは手順 7 の突き合わせ後、simplify 実行前の保存は報告後にユーザーが戻す・戻さないを決めた後に削除する。

**読み取りが拒否されているファイルの除外**: `~/.claude/settings.json` とプロジェクトの `.claude/settings*.json` の `permissions.deny` にある `Read(...)` に該当するファイル（例: `.env`、`secrets/**`、`config/credentials.json`、`*.pem`、`*.key`）は、一時ファイル経由で複数のエージェントに露出させないため、diff ファイルと simplify のコピーに含めない。pathspec で除外し（例: `':(exclude).env'`、`':(exclude,glob)**/*.pem'`）、未追跡の `--no-index` 追記、突き合わせの期待一覧、書き換え可能なファイルからも除く。本体もその内容を読まない。除外したファイルは、手順 7 の総評に「権限制約により未レビュー」と記載する。

1. **simplify**（質問 2 で承認された場合のみ）
   * 書き換え可能なファイル（手順 3）が空なら、スキップして報告する。
   * 実行前に、次を保存する（コミット ID などはスクラッチパッドのファイルにも書き出す）。(a) `git stash create` の出力（tracked の未コミット変更のスナップショットのコミット ID。空なら `HEAD` を使う）、(b) 未追跡ファイルの一覧とハッシュ（`git ls-files -o --exclude-standard -z | xargs -0 -r sha256sum --`）、(c) 質問 3 で含めた未追跡ファイルのコピー（`cp --parents -- <ファイル> <宛先>`）。`--` は、先頭が `-` のファイル名がオプションと解釈されるのを防ぐ。
   * サブエージェントには、書き換え可能なファイルの一覧を指示文で渡し、それ以外の変更とファイルの新規作成・削除は禁止する（質問 3 で「含めない」を選んだ未追跡ファイルと gitignore 対象は、コピーがなく復元できず、gitignore 対象は事後の検出もできないため、特に触らせない）。diff ファイルは、この時点ではまだ無いので渡さない。他のレビューより先に単独で実行し、結果は、変更したファイルの一覧と要約で返させる。完了（または未完了の確定）まで、手順 6-2 に進まない。
   * 完了後、パス指定なし（リポジトリ全体）で `git diff --name-status <スナップショット>` を実行し、未追跡ファイルの一覧とハッシュを取り直して前後を比べ、変更・新規作成・削除されたファイルを特定する。書き換え可能なファイル以外の変更や、禁止した新規作成・削除は、違反として報告する。未完了のときは、再実施せず、同じ方法で状態を確認し、手順 6-2 に進むか中止するかをユーザーに確認する。
   * 戻す場合は、`git restore --source=<スナップショット> --worktree -- <ファイル>`（未追跡はコピーから復元）を案内する。禁止に違反して新規作成されたファイルは `git restore` では戻せないので、削除を案内する。コピーのない未追跡ファイルが書き換え・削除された場合は、復元できない旨を報告する。gitignore 対象の変更は検出できないため、サブエージェントの申告に頼り、検出不可と注記する。勝手に戻さない。
   * simplify が変更したファイルは、質問 2 のとおり、手順 4 でスキップと判定していても、最終構成のレビューを再実施する。
2. **レビュー対象の diff ファイルを作る**（simplify を実施した場合は、実施後の状態で）
   * `git diff <比較範囲> [-- <パス>]` の出力を保存する。未追跡ファイルを含める場合は、`git diff --no-index -- /dev/null <ファイル> || true` の出力を追記する（リポジトリルートからの相対パスで渡す。バイナリは除外して注記し、突き合わせの期待一覧からも除く。除外したバイナリは、手順 7 の総評に「未レビュー（バイナリ）」として記載する）。
   * 変更ファイルのみ再実施するレビューには、対象ファイルだけの diff（`git diff <比較範囲> -- <対象ファイル>`、未追跡は `--no-index`）を、レビューごとの別ファイルとして作る。対象ファイルは、（手順 4 で変更ありと判定したファイル ∪ simplify が変更したファイル）∩ 絞り込みパス。simplify を実施した場合は、手順 4 でスキップと判定したレビューも含み、ユーザーが外したレビューは含まない。
   * レビューごとの対象ファイル一覧と、その diff ファイルのファイル一覧を突き合わせ（全体は `git diff --name-only <比較範囲> [-- <パス>]` と、質問 3 で含めた未追跡ファイルの一覧の和集合と比べる）、漏れがないか確認する。規模は再計算しない。
3. **以降を並列で実施する**
   * `/code-review` / `/security-review`: `general-purpose` サブエージェントをバックグラウンドで並列起動し、Skill ツールで呼び出す。1 つのサブエージェントでは、1 つのスキルを 1 回だけ実行する（同じコンテキストでは 2 回目に再展開されない）。
   * my-review 本体: メインで実施する（要件の文脈が会話にあるため）。最新の diff で行う。
4. **全サブエージェントの完了を待ってから**手順 7 に進む。

**サブエージェントへの指示に含める内容**（simplify は手順 6-1）

* 対象の diff ファイルの絶対パス（`/security-review` は args が反映されないため指示文で渡す。`/code-review` は args にも書く）。2000 行を超える場合は offset / limit で最後まで読み、Read がエラーなら limit を下げて分割して読む
* `/security-review`: args なしで呼び、次を指示する
  * テンプレートが取得した diff（DIFF CONTENT など）ではなく、必ず diff ファイルを対象とする。テンプレートの diff が空でも「変更なし」と判断しない
  * diff ファイルは Read で読む（テンプレートの「Bash を使わない」に従う）
  * 手順 3 のリスクフラグを渡し、認証・認可・バリデーションは実装箇所まで追跡して確認する。結果は「認証 / 認可 / データ漏洩 / 入力値検証」の 4 軸も含めて返す
* `/code-review`: args は `<レベル> <diff ファイルの絶対パス>`（例: `medium /path/to/review-target.diff`）。レベル（`medium` / `high`。「Other」で指定された `low` / `max` も可）を先頭に置き、半角スペースで区切る。文章を混ぜるとレベルが認識されず、レベルを省略すると前回の値が使われる。レベルだけを渡すと、スキルは作業ツリーの未コミット変更を対象にする。git の書式や範囲の説明は args に書かず、simplify との重複を避けるため正しさ・バグに限定して返すよう、指示文で伝える
* スキルの結果にかかわらず、diff ファイルを直接読んで確認し、「スキルの結果」と「直接確認」を区別して返す（`/security-review` は確信度 8 未満の候補を落とすため、実害のある指摘が 0 件になり得る。除外された候補も併記する）。実際に確認した対象ファイル一覧も含める
* Skill がバックグラウンド実行を返した場合、またはスキルが内部でサブタスクを起動した場合は、完了通知を受け取るまで待ち、最終結果をそのまま返す。待つ間は読み取りのみのツール呼び出しを続ける（`Monitor` の until ループでもよい。上限を決め、超えたら「未完了」）。起動しただけ、「待機中」などの途中経過だけで返答を終えない。待てない場合は「未完了」と明記して返し、メインは、そのレビューを未レビュー扱いにして再実施またはフォールバックに回す（simplify は再実施せず状態を確認する）。サブエージェントの途中経過は最終報告として扱わず、完了通知とその後の最終報告を待つ
* 重点観点（他の観点も省略しない）と、変更の目的・要件（会話から要約）
* `--fix` / `--comment` は付けない。ファイルを変更せず、外部へ投稿しない。結果は「重要度・`ファイル名:行番号`・問題・影響・修正案」の形式で返す
* Skill ツールが使えない、またはサブエージェントが失敗した場合は、同等の観点を直接指示する。「実施したレビュー」に明記し、モデルや範囲が承認した構成から変わる場合は、実行前に再承認を取る

サブエージェントの結果は、手順 7 の「実施したレビュー」（エージェント名・モデル・委譲内容・概要）に集約して報告する。

**my-review 本体の観点**（重点観点があれば、それを優先して深く確認する）

* **要件適合**: 変更が意図した目的を正確に達成しているか。要件が会話から分からない場合は「要確認」とする
* **互換性・影響範囲**: 既存仕様・API 契約・データへの影響、破壊的変更、呼び出し元・依存先への波及がないか
* **既存実装との整合性**: 既存の設計・規約・命名規則と整合しているか
* **命名・可読性**: 名前が意図を正確に表しているか。将来の保守性を損なわないか
* **検証可能性**: テスト・ログ・実行結果などで動作を確認できるか。テストの有無・不足を確認する

### 7. 統合して報告する

* 本体とサブエージェントの指摘を一本化し、重複はマージして由来（`my-review` / `code-review` / `security-review` / `前回レビュー`）を併記する。
* サブエージェントが報告した対象ファイル一覧を、diff ファイルのファイル一覧と突き合わせる。漏れは、再実施するか、未レビューとして明記する。その後、diff ファイルを削除する。
* simplify を実施した場合は、変更の内容、スナップショットのコミット ID、未追跡ファイルのコピーの場所と戻し方を報告し、戻す・戻さないを確認する。決まったら、保存したファイルを削除する。
* 番号付け: 初回は重要度順に `#1` から振る。同一会話に既存の `#N` があれば番号を維持し、新規は最大番号の次から末尾に追記する。前回と同一の問題（同じファイル・同じ原因なら行番号が動いても同一）は既存の番号を使い、解消したものは番号を残して「解消済み」と記す。欠番にせず、再採番しない。
* 未実施のレビューは総評に明記する: `/security-review` →「セキュリティ未レビュー」（リスクフラグがあるときは特に）、`/code-review` →「バグ・エッジケース未レビュー」、`/simplify` →「冗長・再利用・効率は未レビュー」、読み取り拒否で除外したファイル →「権限制約により未レビュー」。

## 注意事項

* diff のみで「問題なし」と判断しない。推測で判断せず、不明な点は「要確認」とする
* 修正の相談・確認など後続のやり取りでも同じ番号を維持し、再採番しない
* ユーザーの承認なしにレビューを実行しない（手順 5）
* 修正案は提示するが、実際の修正（simplify を含む）はユーザーの許可を得てから行う
