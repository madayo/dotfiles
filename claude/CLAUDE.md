# スキル

指示に応じて、対応するコマンドを選んで実行する。選んだコマンドと理由を一言伝えてから実行する。ユーザーがコマンドを直接指定した場合は、それに従う。「〜できるか？」のような質問には、コマンドを使わず回答だけを返す。

依頼に「worktree」が実行方法の指定として含まれる場合は worktree モードとし、実装には `/my-implement-wt` を使う。ただし、質問への回答とコマンドの直接指定を優先する。話題としての言及（例:「worktree について調べて」）は対象外。迷ったら質問する。コマンドを伝えるときは、worktree モードかどうかも添える。

| 依頼 | コマンド |
| --- | --- |
| 原因・既存動作・変更影響の調査 | `/my-investigate` |
| 変更方針の設計・比較 | `/my-design` |
| 実装・修正と検証・セルフレビュー | `/my-implement` |
| 実装・修正（worktree モード。検証は保留） | `/my-implement-wt` |
| worktree モードで保留した検証の再開（「メインが空いた」「戻って再開」など） | `/my-verify` |
| 変更のレビュー構成の提示・実行 | `/my-review` |

## 推奨する使い方

必要な工程だけ使う。すべてを順番に呼ぶ必要はない。

| 状況 | 使い方 |
| --- | --- |
| 現状の仕様や動作を知りたい | 調査のみ |
| 原因不明の不具合 | 調査 → 設計 → 実装 → レビュー |
| 原因が明確な局所修正 | 実装 → レビュー（方針が未承認なら実装の中で提案・承認） |
| 要件が明確な機能追加 | 設計 → 実装 → レビュー |
| 既存構造が不明な機能追加・リファクタリング | 調査 → 設計 → 実装 → レビュー |
| 認可・決済・DB 変更など影響が大きい変更 | 設計 → 実装 → 重点レビュー（必要なら先に調査） |
| 文言・コメントだけの変更 | コマンド不要。レビューは必要に応じて提案 |
| 並列で進めたい（worktree モード） | 設計（メイン）→ 実装（`/my-implement-wt`）→ メインが空いたら `/my-verify` → レビュー |

## モデルと推論レベルの提案

コマンドを伝えるときに、推奨するモデルと推論レベルも添える。切り替え（`/model`、`/effort`）はユーザーが行う。現在値が推奨と同じなら省略する。現在の推論レベルが分からないときは、推奨値だけを伝える。

初動は、依頼文から次の表で機械的に決める。どの行に当てはまったかも添える。判定は暫定で、調査後に見直す。複数の行に当てはまる、どの行にも当てはまらない、または迷うときは、重い方を選ぶ。

| 判定 | 推奨 |
| --- | --- |
| 影響が大きい（認可・決済・DB・マイグレーション・公開 API）、原因不明、戻しにくい変更のいずれか | Opus / high |
| 要件が明確で、複数ファイルにまたがる。または局所修正でも検証手段がない | Opus / medium |
| 現状の仕様や動作の調査のみ（実装なし） | Sonnet / high |
| 原因と修正箇所が明確な局所修正で、テストや型で検証できる | Sonnet / medium |
| 文言・コメントのみ | Sonnet / low〜medium |

作業中に grep や調査の結果で判定の行が変わる場合は、必ず提案する。同じ行に収まる変動では提案しない。

- 提案は、調査結果の報告や設計の承認依頼など、工程の切れ目にまとめて伝える
- 上げる方向で、承認待ちでなく、必要な文脈（目的・対象・制約）を依頼文にまとめて渡せるときは、先に進められる重い作業（影響調査・レビューなど）をサブエージェントに委譲して進める
- 下げる方向は、機械的な作業（定型の修正・検証の実行・整形など）を、下の条件を満たすときにサブエージェントに委譲して進める。メインの切り替えは、残りの作業が大きいときだけ工程の切れ目で提案する
- 委譲するときは、`model` と `effort` を判定表の推奨値で指定する。コマンドに指定がある場合は、それに従う。`fork` は親の設定を引き継ぐので使わない
- 設計判断はメインで行う。セルフレビューは「作業ルール」のとおりサブエージェントで行う。それ以外は、判断が不要な作業だけを委譲する

### 下げる方向の委譲の条件

次の3つをすべて満たすときだけ、下げる方向で委譲する。1つでも満たさない、または迷うときは、メインで行う。

- 対象が5ファイル以上、または出力が数百行以上になる見込み
- 直前の議論や設計意図が不要で、依頼文だけで完結する
- 結果の判定が機械的（テスト通過、grep の件数など）

### 記録と評価

一連の調査・実装が終わったら、最終報告の直前に `~/.claude/model-routing-log.md` に1作業1行で追記する。書き込みの承認待ちで作業が止まらないよう、他の作業をすべて終えてから行う。ファイルがなければ、見出し行つきで作成する。最終報告にも次を含める。

- 日付、プロジェクト（ディレクトリ名）、依頼の要約（機密情報や顧客情報は書かない）
- 初動の判定行と、最終的に妥当だった判定行
- 切り替え提案の回数と、採用された回数
- 委譲の回数と、委譲先のモデル・effort・作業内容
- 委譲後の手戻りの有無
- 所感（過剰・不足・問題なし）

トークンやコストの実測値は見えないので、推測で書く場合はそう明記する。ユーザーに求められたときは、ログを読んでこの体制の効果を評価する。1回分では傾向を断定しない。

# 作業ルール

- 3ステップ以上のタスクは必ず Plan モードで開始する（承認済みの方針を実装する場合と、調査のみのタスクを除く）
- コマンドを使わない実装でも、実装後のセルフレビュー（サブエージェントで実施）は、`~/.claude/commands/my-implement.md` の「セルフレビュー」節を Read して、その手順に従う

# サブエージェント

使用基準は各コマンドに記載する。サブエージェントを起動した際は、以下を報告する。

- 使用したエージェント名
- 委譲した作業内容
- 返ってきた要約の概要
